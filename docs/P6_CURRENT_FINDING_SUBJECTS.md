## Contract and replay

The failure is a mismatch between the provider Schema and the typed validation rules. `InvestigationSubjects.FindingRefs()` lists all authorized finding targets, including historical alarms and inspected points. In v3.3, `ForModel()` used that list for every finding. `ParseAndValidate()` also requires every target of an affirmative current equipment finding to have a trusted latest point snapshot and cite its Evidence ID. The fourth captured response selected both the alarm and the VIB point. The VIB snapshot was cited and the alarm had no point snapshot.

The v3.4 provider Schema uses a nested `anyOf` under `findings.items`. `AlarmEvent`, `Recovery`, current `MeasurementChain`, and current `EquipmentCondition` with `Inconclusive` keep the existing authorized target set. The affirmative current equipment branches use subject enums derived from the latest point snapshot in frozen ledger order. `NoAnomalyFound` excludes points with a present anomaly. When there are no eligible targets, the corresponding branch is omitted. When both affirmative statuses have the same eligible set, they share a branch. The v3 JSON fields, prompt instructions and server validator are unchanged. The server checks the relationship between subject IDs and their latest snapshot citations. Whether the cited facts support the interpretation still requires semantic review, including cases with trusted readings and insufficient threshold information.

An independent JSON Schema Draft 2020-12 validator checked both Schema documents and replayed both original completions against the frozen 18 Evidence items. The fourth completion, SHA-256 `cd6a15e06493cbbe8543257b2838d3cbb1927196c6745f92847d70623ee58973`, passes v3.3 and fails v3.4 only at `$.findings[2]`. The unchanged service validator still reports `advice-current-evidence` at that path. The third completion gains one Schema error at `$.findings[3]` for the same current-target problem, in addition to the three Evidence ID errors already detected by v3.3. Root readiness for that response still fails on the server. The historical and recovery findings in the captured completions pass the new finding shape.

Each finding branch declares the same required keys and sets `additionalProperties` to false. The root remains an object. The design uses documented nested `anyOf`, enums and local definitions already used by the work-order Schema. It does not use root `anyOf` or conditionals outside the documented subset. Compatibility with the configured relay for this exact revised Schema remains untested. ## Request size and budget

The request comparison uses the production serializer and preserves the previous prepared request's system prompt, frozen evidence, tool results, model, streaming settings and output allowance. The user message carries the new request version. All sizes are UTF-8 bytes.

The frozen request grows by 1,706 bytes (9.0%) and reserves 20,915 units under the Engine's conservative request-size check. The captured final request allows 5,863 output tokens. The production service captures the alarm point and up to two related current points. The 40-item fixture with that number of distinct current points reaches the local gateway within the existing 32k input / 6k output limits. The synthetic 39-point stress case reached the v3.3 local gateway. With v3.4 it requires 35,853 input units after compaction and fails before the gateway. It represents a broader point scope than the current service supplies. Retain this budget check if the service later increases point coverage. Reported model token usage for v3.4 is unknown.

The existing `$defs` reuse one array Schema per eligible target set. An offline prototype partitioned the UUIDs into three disjoint enums and rebuilt each target set with item-level `anyOf`. With one anomalous point, it added 126 Schema bytes for three points and saved 2,682 bytes for 39 points, less than the 3,853-byte shortfall. The direct enums remain easier to inspect. The budget regression test covers zero and three distinct current points reaching the scripted gateway and the synthetic 39-point request stopping before a model round.

## Default-budget CI regression

PR #5 exposed a separate request-projection regression at the default 16k input / 2k output limits. Both heating fixtures completed their reads but the final request exceeded the input allowance. The on-demand read fixture lost its query-watermark warning from the projected model input. The compact projection retains the first service-ordered data-quality fact and skips window metadata when the trend has neither visible facts nor numerical change. If the resulting request still exceeds the allowance, the Engine drops lower-priority trend summaries before alarm-point summaries and checks the serialized request again. Current snapshots and the leading warnings stay visible. The model can have less trend context at the default limit. Frozen evidence, tool deadlines, the provider Schema and the server validator are unchanged. Request diagnostics record the required bytes and either the resulting trend count or the remaining allowance on rejection.
