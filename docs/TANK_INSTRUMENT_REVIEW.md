# 储罐液位仪表案例评审

三例使用本机只读 OPC UA、MeasurementWorker、隔离的 plantops_tests 和项目的 v3 调查服务。事故来源是美国化学安全委员会 CAPECO 调查报告第 6.5.1 节及附录时间线。504 号罐的浮子钢带装置卡住，409 号罐的液位及由它推算的充装速率无法在计算机上实时取得。操作人员另有人工读数。[CSB 最终报告，第 39 页](https://www.csb.gov/assets/1/20/capeco_final_report__10.21.2015.pdf#page=39)

## 模型可见证据与预先约定的判据

罐号、厂名和事后结论均未进入模型材料。截面积 10 平方米、液位分辨率 0.01 米、独立进出口流量计、数值、时间线及历史告警均为本项目构造。三例共用一次历史液位告警及恢复，供项目从同一类入口发起调查。比较最早从第 18 秒开始，复验入口等待实际入库的告警恢复后再进入比较段，检查实际入库的时间、数值和质量。进料与停料两例使用相同的液位值及生成规则，协议传输导致实际样本时间和数量可能有差异。

| 条件 | 关键判断 | 值得采纳的下一项检查 | 需要拒绝的推论 |
| --- | --- | --- | --- |
| 进料，自动示值恒定 | 入口 360 m³/h，出口 0，自动点持续收到 5.00 m Good。在观测重叠且流量具代表性的条件下，按罐截面推算每 10 秒应升约 0.10 m，超过显示分辨率。 | 对齐同一时间段的独立液位记录、进出口计量与自动示值，区分测量链异常和工况记录不一致。 | 单凭 Good 认定示值准确，或指定浮子卡死。 |
| 自动点断更 | 最后一条自动读数为 5.00 m。比较开始后第 6 秒的独立人工记录为 5.06 m，只对应一次读数。流量点继续更新。 | 核对最后有效源时间、单点传输与记录到达时间，取得同时间的独立读数。 | 把人工读数或最后 Good 外推成当前实测液位，把单点断更泛化成全站断线。 |
| 停料，自动示值恒定 | 进出口都读 0，自动点仍持续更新 5.00 m。该段示值与已知工况相容。 | 把历史告警恢复和当前稳定分开；需要判断仪表响应时核对已有的工况变化和独立记录。 | 因恒值直接判为卡死，或因短时相容就排除仪表故障。 |

核查的是模型实际拿到的资料。如果某点未进入模型证据，单独记录取证范围。回答评审以含义为准，分别记录事实、关键遗漏、过度推断和检查是否有区分作用。无回答单列为可用性结果。公开案例及编写者可见的判据不计入独立留出集。工程师先答、后看 AI 的记录可使用[同案评审表](PORTFOLIO_PAIRED_REVIEW.md)。

## 复验入口

在 PowerShell 7 的仓库根目录设置指向 plantops_tests 的 PLANTOPS_TEST_CONNECTION 并还原项目依赖。以下命令默认使用 Fake，只用于验证链路。每次使用新的 Run 名。

```powershell
./deploy/Test-TankInvestigation.ps1 -Case filling -Run tank_fill_local
./deploy/Test-TankInvestigation.ps1 -Case missing -Run tank_missing_local
./deploy/Test-TankInvestigation.ps1 -Case idle -Run tank_idle_local
```

真实模型另传 -RealAi、当前授权的 -LedgerPath 和对应的 -MaxRequests，可用 -Model 指定同一服务上的对照模型。每案上限四轮，自动重试为零。每例的 protocol.json 保留预检时的协议样本，investigation.json 保存调查服务随后冻结的证据、模型结果和逐轮诊断。逐条评审采用后者的调查截止时刻。测试不会提交或执行工单。
## 本轮证据与调整

2026-11-21 使用新授权账本（上限 100 个外部请求）。模型服务为项目本地配置的服务。首轮默认模型 gpt-6.1-sol 返回 HTTP 502，后续选择同一服务上的 gpt-6.2-sol 作对照。模型服务响应、应用接受回答、建议内容的逐条核对分别记录。下表由 Codex 对照原始样本、冻结证据和模型回答复核，独立工程师首答数为零。

| 版本与案例 | 结果和依据 |
| --- | --- |
| v3.17，进料 | 默认模型首轮 502。对照模型完成两轮，在尚未得到恒值段边界时，只给出若净流入持续则每秒应升 0.01 m 的条件推算。最终一项发现列出 11 个证据引用，上限为 8，应用拒绝交付。[默认模型回执](../artifacts/opcua-runtime/tank_fill_a/investigation.json) · [对照模型回执](../artifacts/opcua-runtime/tank_filling_b/investigation.json) |
| v3.17，断更 | 回答可交付。F5 分别给出自动点历史值 5.00 m、人工点历史值 5.06 m 和当前入口流量 360 m³/h，说明前两者时刻不同。R1 要求核对同期新样本、质量、独立点测以及覆盖边界。调查工具限取两个关联点，此例选中入口和人工点，出口没有进入模型证据。首次协议预检因数据库时间精度误拒，修正后通过，首次未调用模型。[预检失败记录](../artifacts/opcua-runtime/tank_missing_a/protocol.json) · [调查回答](../artifacts/opcua-runtime/tank_missing_b/investigation.json) |
| v3.17，停料 | 可交付。模型读到两个零流量，避免了断言仪表卡死，但只能核对单点和全窗首末值，明确表示无法引用末段稳定时长。历史液位下降和当前停料阶段被分别讨论。[调查回答](../artifacts/opcua-runtime/tank_idle_b/investigation.json) |
| v3.18，进料 | 修复取证后，E10、E12、E14 的同值段重叠 16 秒，液位 5.00 m、进流 360 m³/h、出流 0。原始回答正确算出条件净增 1.6 m³、应升 0.16 m，并说明具体原因仍未知。应用仍因单项引用超限拒绝交付；该解释只计为对原始输出的评审。[调查回执与冻结证据](../artifacts/opcua-runtime/tank_filling_c/investigation.json) |

补齐时间边界后的停料案也得到可交付回答。F5 给出末段 25 个液位样本均为 5.00 m，F6 给出各 37 个零流量样本。模型未误报卡死，但仍未直接说明当前三条示值相容，且把重点放在共同的历史液位下降上。[v3.18 停料回答](../artifacts/opcua-runtime/tank_idle_c/investigation.json)

第一处调整属于证据摘要。原算法在整个窗口可计算变化量时，可能只呈现首值和末值。新算法还呈现最后一串连续相等、逐点通过质量和时间校验的实际样本，记录起止、最小值、最大值和个数。它能区分“先变后稳”和“始末相等但中途变化”，也能用非液位的温度样本复验。遇到已有缺口时沿用有界末段，截断与无效尾样本不生成新段。该摘要不能证明采样间物理状态。

第二处调整属于作答契约。两份进料回答都将多项证据堆入一条发现，产品拒绝了超限列表。v3.19 向模型明确每个列表至多八项，要求选择直接依据并拆开独立结论。服务仍验证所有引用。误拒风险是有用解释无法交付，误采风险是精简引用后丢失区分原因所需的独立证据，两者在复验中分别检查。

历史告警用于进入调查流程，早期液位从 5.20 m 变为 5.00 m 时两路流量均为零。三例都有这一人工构造的历史矛盾；指出它是合理的，但不能代替对恢复后比较段工况的判断。同一案例的各轮使用相同生成规则；采集时刻、连续段长度、模型的取证选择均可能不同。

## 最终版本 v3.19

进料复验产生可交付回答。F6 用 E3 的罐截面和 E10、E12、E14 的共同区间核算：18 秒内条件净增 1.8 m³，应升 0.18 m，但同期自动读数维持 5.00 m。R1、R3 分别建议核对三路信号来源、对时和同期独立读数，答复中未认定某一测点失准。该次发现最多引用 6 项，直接复算所需的四项依据均能从 F6 打开。[进料最终回答](../artifacts/opcua-runtime/tank_filling_e/investigation.json)

停料和断更在 v3.19 的首次有效发起均在第一轮收到 502，应用没有回答。[停料回执](../artifacts/opcua-runtime/tank_idle_e/investigation.json) · [断更回执](../artifacts/opcua-runtime/tank_missing_e/investigation.json)

另有一次断更预备运行已采到有效数据，但固定时间冻结自动点后，数据库仍记告警 Active，未满足三案共用历史恢复告警的入口条件，未发模型请求。现改为等数据库实际记下触发及恢复，再开始比较段。修正后停料和断更均通过真实协议预检。[预备运行](../artifacts/opcua-runtime/tank_missing_c/protocol.json) · [修正后的断更预检](../artifacts/opcua-runtime/tank_missing_e/protocol.json)

停料对照的独立证据是进、出口两个计量点。仿真器知道没有进出料；模型没有看到单独的班组停料确认记录。对模型的判据是“同期观测相容”，对确切操作状态保留未知有依据。三例均未在现场操作或验证，亦未做独立工程师首答。误采率、误拒率和节省工时仍无实测依据。

## 验证范围

- OPC UA 单位与映射 39 项通过。液位仅接收 m，体积流量仅接收 m3/h，按 OPC UA 工程单位身份、映射的物理量及换算参数校验。
- 证据调整后的定向回归 100 项通过，含隔离数据库、非储罐温升、坏值、截断和历史兼容测试。v3.19 初稿增加提示长度后暴露一例最小输入预算回归，压缩说明后最终定向回归 54 项通过，含六个有界输入用例。最终无数据库凭据的全套运行 718 项通过、154 项跳过、0 失败。未运行全部数据库集成、浏览器或部署验收。
- 新的确定性分支只计算相等样本的已验证时间范围；模型解释不同测点间的关系。提示正文较 v3.17 减少 9 个字符，末段证据会增加输入长度，沿用原投影和限额。输出 schema、证据权限、只读工具和审批沿用原机制，没有通过调大预算或放宽引用校验来取得答案。

### 服务可用性与结构失败

同一配置下再次运行停料和断更，两次首轮均为 HTTP 502。随后用项目默认 gpt-6.1-sol 做交叉检查，停料首轮仍为 502，断更得到两轮 HTTP 200。默认模型的原始摘要正确区分了两条旧液位记录和新鲜入口流量，但输出了 9 项发现，契约上限为 8，最终用户没有取得这份回答。该次拒绝说明精简引用不能保证模型遵守所有数组限制。[停料复验](../artifacts/opcua-runtime/tank_idle_f/investigation.json) · [断更复验](../artifacts/opcua-runtime/tank_missing_f/investigation.json) · [默认模型停料](../artifacts/opcua-runtime/tank_idle_default/investigation.json) · [默认模型断更](../artifacts/opcua-runtime/tank_missing_default/investigation.json)

末轮断更复验取得 v3.19 正式回答。F5–F8 指出自动液位末段与入口流量末段仅边界相接，同期可计算时长为零。R1、R2 要求先核对采集链路和取得同期独立液位；R3 正确要求补出口计量。R4 声称整次调查没有可用的文档检索工具，这一说明应拒绝：首轮请求实际提供了 search_documents，模型仅选择了测量读取；最终作答轮没有提供工具。已核对模型实际收到的请求和工具选择。该语义错误不会被引用数量或 JSON 校验识别。[断更最终回答及逐轮记录](../artifacts/opcua-runtime/tank_missing_g/investigation.json) · [同批停料服务失败记录](../artifacts/opcua-runtime/tank_idle_g/investigation.json)

停料的最后一次 v3.19 复验，首轮成功选取测量，冻结证据显示三点有 25 秒共同观测：液位 5.00 m、进出口均为 0 m³/h。最终作答请求返回 502。该版本没有可评的停料建议。可评的停料回答来自 v3.17 和 v3.18。[最后一次停料回执](../artifacts/opcua-runtime/tank_idle_h/investigation.json)

**总计**：16 次真实模型调查，产生 5 份可交付回答；8 次调查因 HTTP 502 未完成，3 次因结构校验拒绝。新账本使用 25/100 个外部请求，其中 17 个 HTTP 200、8 个 HTTP 502，自动重试为零。最终 v3.19 的 10 次调查中，进料与断更各取得 1 份可交付回答，停料为 0 份。其余运行均保留。重复案例、不同版本和两种模型使这些计数只适合解释本轮运行；没有真实现场准确率或可靠率估计。
